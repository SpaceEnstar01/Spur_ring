# Agent 回复与后台分析

本次复用 Java、当前硅基流动模型及现有持久化数据库，不新增 Python 服务、云资源或模型订阅。默认模型仍为 Qwen/Qwen3-8B，线上可由 SILICONFLOW_MODEL 覆盖；未做真实模型横评，不能据此宣称准确率提升了某个百分比。

## 回复行为

- 普通知识、比较、明确分析请求、文案/脚本草稿走只读回答，不只输出意图分类。
- 简单陈述仍走原有意图链路。idea 摘要应包含价值、关键风险与可验证的下一步；不是用户决定，也不自动变成长期记忆。
- 闹钟、发送、承诺、修改、撤回及混合请求继续走原有结构校验与执行策略。instruction + none 的文字回答不再生成“未接入工具”的动作卡。
- 明确追问最多附带本设备工作区最近 24 小时内的两条只读问答或想法记录，排除带工具、承诺、已删除、旧转写版本及失败记录；不附带所有录音或个人资料。参考资料不代表新授权；多个可能指代应澄清。普通独立问题不附带历史。
- 明显语病可整理，产品名、人名等有歧义时应澄清。没有联网工具，不声称搜索过或给出未经核实的实时价格。
- 结构提取 temperature=0.1；文字解答 temperature=0.4。保持现有模型和输出长度限制。

## 异步契约与发布顺序

新版 APP 在提交 /records 和 /records/{id}/retry 时发送 X-Spur-Async: true。Java 先持久化原文，立即返回 schemaVersion=1 的工作区（received/interpreting），后台按已有数据库中的待处理记录生成结果。APP 前台每约 3 秒查询工作区，完成后停止；查询不重复提交录音、不重复调用模型。APP 不在后台创建新的系统动作。

旧 APP 不发送此头，保留同步返回契约。因此可先发布 Java，再更新 APP。旧服务器忽略额外请求头，新 APP 仍兼容其同步结果。完整的等待体验需要更新 APP，不能仅部署 Java 后宣称全部生效。

后台 worker 默认随 Agent 启用，单线程按接收时间处理。待处理原文就是持久化队列，不依赖内存 Future；重启后会处理 received，回收超过 180 秒的 interpreting。不自动重试 failed；用户显式重试仍受原有状态校验。新版转写会终止旧版的待处理状态；删除、版本及运行标识校验阻止迟到结果恢复旧内容。worker 只做分析和内部策略处理，设备工具仍需原来的许可/回执流程。

当前小规模内测扫描工作区聚合寻找待处理记录，沿用现有容量限制。扩大用户规模前应改成有索引的独立任务表和公平调度；本次不引入外部队列。持续模型故障会保存失败状态，不无限调用上游。部署继续保持 H2 持久卷、单副本和 Recreate。

## 验收场景

| 录音 | 期望 |
| --- | --- |
| 为什么电动车冬天续航下降？ | 直接解释原因，不生成动作卡 |
| 小米汽车和特斯拉有什么区别，适合谁？ | 说明比较维度及条件，不编实时价格 |
| 我想拍一期 AI 眼镜视频，帮我分析可行性和下一步 | 核心想法、关键风险、具体下一步 |
| 帮我写一个介绍小米汽车的短视频脚本 | 返回草稿，而不是说“你想写脚本” |
| 我喜欢先看简洁方案 | 保存为陈述，不误当成问答或自动记忆 |
| 那它有什么优缺点？ | 仅参考近期有效问答，歧义时澄清 |
| 帮我分析方案，然后明天九点提醒我 | 保留完整意图/闹钟校验，不走只读快捷路径 |
| 把这份脚本发送给客户 | 明确缺少发送能力，不冒充已发送 |
| 请求很慢、APP 切到后台后回来 | 前台查询持久化状态，不重新提交模型请求 |
| 处理中修改或删除转写 | 迟到结果不覆盖新版或恢复已删除内容 |

自动测试使用模拟模型和本机 HTTP fixture，验证路由、上下文范围、无工具副作用、持久化任务和客户端轮询。它们不衡量真实模型答案质量。发布后需用上述样本及用户实际失败样本复核内容，再决定是否在同一数据集上比较更强模型的效果、耗时与费用。
