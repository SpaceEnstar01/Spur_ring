# 模型超时与连接失败

异步提交只消除了 APP/网关长连接等待，并不能保证上游模型服务成功。上线后仍有模型超时和快速返回的 UPSTREAM_CONNECTION；没有服务端异常类别和运行 Pod 的网络探测，不能断定是模型排队、DNS、TLS、网络出口还是供应商故障。

本次不更换模型、不新增云资源，也不认为延长超时就解决了问题：

- 非流式推理最多两次，每次最多 30 秒，间隔最多一秒，仍受全局 4 个模型并发限制。不会在 APP、worker、模型客户端三个层面叠加无限重试。
- 只有传输超时、IO 连接故障、HTTP 429/502/503/504 允许第二次尝试。认证失败、空内容、无效 JSON、结构校验失败不自动重试。供应商明确要求超过一秒的 Retry-After 时不立即重复请求。
- 普通文字回答默认 100～350 字，max_tokens=1024。结构意图保持 4096 的上限。不完整的 finish_reason=length 结果不可当成成功回复或操作建议。
- SILICONFLOW_FALLBACK_MODEL 可选配置同一供应商的备用模型，默认空，第二次仍使用原模型。没有未经验证就选择一个付费模型，也没有自动换用新的第三方。
- 日志仅包含尝试次数、耗时、固定 DNS/TLS/connect/transport 分类及状态码，不输出 API Key、录音转写或供应商响应。可用日志区分“连接失败”和“等待完整生成超时”。
- 重试只发生在模型文本推理阶段。不会重试闹钟等真实设备操作，不放宽原文证据、权限或回执校验。两次推理可能产生两次供应商计费，遇到持续网络故障仍会失败并保留来源。

验收使用本地 HTTP fixture 模拟延迟首个请求、服务繁忙、备用模型、认证失败、供应商退避、无效/截断结果。不能拿这些测试代替 ACK 的出网连通性验收，也不保证模型永不超时。

排查线上时先查看 api 容器的 Model request failed / Model attempt 日志，再在实际运行该容器的网络环境验证模型域名解析及 HTTPS。公网健康检查 200 只能说明应用存活，不能证明模型连接正常。网络问题解决前，不应把一次健康检查当作 AI 链路已修复。
