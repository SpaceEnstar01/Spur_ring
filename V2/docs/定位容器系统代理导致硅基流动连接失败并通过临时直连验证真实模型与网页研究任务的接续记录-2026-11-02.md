## 结论与状态

镜像 `spur-agent:dev` 可以执行真实模型驱动的任务。通过临时受限的直连 CONNECT 通道，真实的“HTTP → DSH → 模型 → 工具 → 成果下载”已通过两项验证。

但 **Docker 默认出站路径仍然失败**。本次将当前阻塞定位到所用代理路径：Docker 设置记录显示继承系统代理，容器代理透明端口为 80/443；Mac 直连官方 API 正常，Mac 显式走同一个系统代理也出现 TLS 失败；绕开该代理路径后容器内原有 TLS 客户端和真实任务均成功。

尚未查明该系统代理访问此域名失败的更底层原因，例如具体代理路由或出口策略；没有证据支持直接断言是供应商封禁、证书失效或依赖版本问题。

**临时通道只用于定位和验证，不是产品部署方案，也没有打入镜像。** 下一步需确认并应用 Docker 的域名级代理绕过设置，再移除诊断通道进行直接复测。当前仍不应宣称 ACK 已部署就绪。

## 临时诊断方式与边界

- Mac 上临时创建只绑定 `127.0.0.1` 的 CONNECT 服务。
- 仅接受 `api.siliconflow.cn:443`，其他目标返回 403；不是开放代理。
- 由 Mac 直接建立到供应商的 TCP 连接，原始 TLS 字节透传；不解密 HTTPS、不记录密钥或请求正文、不关闭证书校验。
- 仅在临时测试容器中设置代理环境变量；供应商地址仍为 `https://api.siliconflow.cn/v1`，没有改为模拟模型或替代模型。
- 使用原镜像、非 root 用户及已验证的 Playwright seccomp 配置。
- 仅注入聊天所需的凭据，不注入邮箱凭据，不调用媒体生成或邮件发送。
- 临时连接方式使 Docker 通过高位端口连接 Mac，避免其 80/443 透明代理路径；它只用于本机对照，不应成为云端前置依赖。

本轮结束前，测试容器已停止并移除，临时 CONNECT 服务已停止，临时凭据文件已删除；诊断证据保留在本地 `.build/network-diagnosis/`，不把该通道留作常驻服务。

## 正式修复建议与待确认范围

优先在 **Docker Desktop 的代理绕过设置**中，为 `api.siliconflow.cn` 增加精确域名例外，保留已有代理地址和其他例外，不关闭整个代理或 VPN，不修改模型 URL，不改变网页工具的 SSRF 边界。

由于这会改变 Docker 的默认网络路径，按前面约定，本轮没有应用该全局设置。具体 GUI/API 字段及是否需要重启应以 Docker Desktop 4.97.0 实际界面为准；若需要改用其他代理模式，须先核对影响，不能直接把全部容器改成无代理。

配置应用后的验收顺序：

1. 关闭诊断通道，在原镜像默认网络中直连官方 API，TLS 正常。
2. 验证真实 Key 的模型列表接口返回 200，不打印 Key。
3. 再执行一次真实模型工具任务，检查成果下载和日志。
4. 保留正常代理路径的公开网页研究能力，确认域名例外未影响其他来源。
5. 完成上述步骤后，再准备 ACK 资源核查及部署配置。

容器应用中的 NO_PROXY 与 Docker 的透明代理不是同一层，不能仅添加应用环境变量就假设已绕过 Desktop 的透明代理。
