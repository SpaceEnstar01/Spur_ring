# Spur 意图识别与 Agent 执行规范

**版本：** V1.0\
**用途：** 供 Spur 工程团队实现意图分类、个人意图状态更新、Agent
自主执行与 App 状态展示。\
**默认策略：** B --- 分级自主模式（Balanced Autonomy）

## 1. 目标与核心原则

Spur
不只是把录音转成文字或摘要，而是把用户主动表达的内容转化为可追溯、可纠正、可持续推进的个人事务。

核心链路：

**Capture → Interpret → Resolve → Update State → Check Permission →
Execute / Ask → Verify → Reconcile**

1.  原始内容优先保存；分类失败不能导致录音丢失。
2.  想法不等于决定，决定不等于授权。
3.  一条录音可以包含多个意图，不强制单标签。
4.  所有关键状态变化必须可追溯到来源、时间和变更原因。
5.  新信息不应静默覆盖旧决定；保留历史并标记有效状态。
6.  低风险内部处理可自动化；外部副作用按授权和风险分级。
7.  低置信度时保存并请求澄清，不得猜测关键人物、项目或日期。
8.  LLM 负责理解与提出变更建议；后端负责校验、持久化、授权、执行和审计。

## 2. 三层数据模型

这三层是不同的数据用途，不是互斥的录音分类文件夹。同一条录音可以写入原始记录、更新语义记忆，并更新某个
Matter。

### Layer 1 --- Raw Memory / Episodic Record（原始事件记忆）

回答：**用户说过什么？当时发生了什么？**

保存原始音频引用（按产品策略）、原始转写、时间、来源（Ring / Phone /
Import）、识别结果、关联对象和后续人工修正。原始记录尽量不可变；模型推断必须与用户原话分开存储。

用途：原文回忆、检索、审计和为后续判断提供证据。

### Layer 2 --- Semantic Memory（语义记忆）

回答：**用户长期偏好什么？通常如何工作？**

例如：偏好真实体验类内容、习惯先看简洁方案、某联系人通常是摄影合作伙伴。

规则： -
只写入有长期价值且有证据支持的信息；单次临时表达不自动升级为长期偏好。 -
保存来源、置信度和最近确认时间；允许用户查看、编辑、删除。 -
语义记忆用于个性化，但不能覆盖用户明确的最新指令。 -
对敏感属性采取更严格规则；没有必要时不推断、不持久化。

### Layer 3 --- Personal Intent State（个人意图状态）

回答：**用户正在推进什么？当前有效决定是什么？接下来发生什么？**

以 **Matter** 为组织单位，建议维护：

-   `matter_id`、`title`
-   `status`: `emerging` / `active` / `blocked` / `waiting` /
    `completed` / `cancelled` / `archived`
-   `goal`、`current_direction`
-   `decisions[]`、`commitments[]`、`tasks[]`
-   `people[]`、`deadlines[]`、`pending_questions[]`
-   `permissions[]`、`source_refs[]`、`updated_at`

每项关键事实或状态变更至少记录：`value`、`source_id`、`observed_at`、`recorded_at`、`confidence`、`validity`、`supersedes`、`change_reason`。

**不要让模型每次凭空重写一份"当前摘要"。**
应通过有来源的事件和状态变更更新状态，并保留历史，以便解释"为什么现在是这个状态"。

**实现注意：** 用户表格中的 `Command` 与本文 Schema 中的 `instruction`
指同一类核心意图。代码层统一使用 `instruction`；UI
文案可以显示"指令"或"执行请求"。分类结果不能直接等同于工具调用许可。

五类描述用户这次表达的主要语用行为，不代表内容只能写入某一层。一个录音可包含多个意图；无法判断时允许
`unknown` / `needs_clarification`。

### 3.1 `idea` --- 想法

**定义：** 探索性、未承诺、尚未明确要求执行的可能性或灵感。

例子："我觉得 AI 眼镜挺值得拍的。"

处理： 1. 保存原始录音和转写。 2. 尝试关联现有
Matter；若无合适对象，可保留为独立想法或提出新建建议。 3.
可以整理或给建议，但不自动变成确定目标、截止任务或外部行动。 4.
想法重复出现不代表用户已作决定。

默认：自动保存与关联；不自主对外执行。

### 3.2 `decision` --- 决定

**定义：** 用户明确选择方向、目标、方案或取舍。

例子："我决定做一期 AI 眼镜视频，重点讲真人体验。"

处理： 1. 定位相关 Matter。 2. 更新目标、方向或有效决定。 3.
与旧决定冲突时，将旧决定标记为 `superseded`，保留历史。 4.
事项或决定有歧义时请求确认。 5.
可以自动更新内部状态；不能把"决定做某事"推断成"授权联系他人或花钱"。

默认：明确时自动更新内部状态；外部行动单独判断授权。

### 3.3 `commitment` --- 承诺

**定义：** 用户对他人承担交付义务，或记录他人对用户的承诺。

例子："我答应摄影师周五给脚本。""Jack 说明天下午把样片发给我。"

处理： 1. 识别承诺主体、对象、交付内容、时间及相关 Matter。 2.
信息充分时创建或更新内部任务/承诺。 3. 区分
`user_owes`（用户欠对方交付）与 `other_owes`（对方承诺交付）。 4.
日期不清楚时不编造日期；可创建无绝对截止时间的任务或请求澄清。 5.
不因存在承诺就擅自向第三方发送消息。

默认：可自动建立内部任务；提醒与外部跟进遵守用户设置和授权。

### 3.4 `instruction` --- 指令

**定义：** 用户明确要求 Spur / Agent 执行动作。

例子："把我的脚本发给摄影师。""把拍摄时间改到周六。"

处理： 1.
提取动作、目标对象、输入材料、收件人/服务、限制条件和期望结果。 2. 解析
Matter 和上下文，避免要求用户重复解释已知信息。 3.
检查工具、参数、授权、风险和重复执行。 4.
在授权范围内执行；缺少信息或权限时进入 `needs_confirmation` 或
`needs_clarification`。 5. 验证工具结果并关联到 Matter。 6.
失败时记录原因和下一步，不得谎报成功。

默认：由权限和风险决定；明确指令不代表所有外部副作用都可无条件执行。

### 3.5 `correction` --- 纠错 / 变更

**定义：** 用户修正先前信息、撤回决定、替换方案、取消任务或指出 Agent
理解错误。

例子："不对，上一版不要了。""刚才说错了，应该是下周一。"

处理： 1. 找到被纠正的事实、决定、任务或执行过程。 2.
区分事实纠正、方案修改、撤销授权和取消任务。 3.
更新当前有效状态并保留旧版本。 4. 检查相关 Agent
Run；安全可行时暂停或取消冲突动作。 5.
已完成且无法撤回的外部操作，要如实说明并提出补救方案。 6.
"上一版""那个项目"等指代不清时先询问，不猜测执行。

默认：明确的内部状态可自动修正；外部取消、重发、通知等遵守权限规则。

## 4. 意图识别 Prompt

### 4.1 输入上下文

给分类模型提供： - 当前转写文本、录音来源和时间。 - 候选
Matter（标题、当前状态、近期决定）。 - 近期相关录音/事件。 -
当前授权摘要和可用工具（如相关）。

不要无差别注入全部用户历史；先检索相关上下文，并注明来源与时间。

### 4.2 系统 Prompt（可直接作为初版）

``` text
你是 Spur 的 Intent Interpretation Engine。
你的任务不是直接执行用户的自然语言，而是识别用户表达的意图，
提取有证据支持的事实与状态变更建议，并指出执行需要的权限判断。

规则：
1. 原始转写是证据。不得把推断写成用户明确说过的事实。
2. 区分 idea、decision、commitment、instruction、correction。
3. 一段话可包含多个意图，按文本顺序输出多个 intent_items。
4. 想法不等于决定，决定不等于授权。
5. 先尝试关联已有 Matter；只有证据充分时才自动关联。
6. 对模糊的人名、项目、日期、代词和“上一版”等指代，不得编造。
7. 明确区分用户承诺与他人承诺。
8. 新旧决定冲突时提出状态变更建议并保留历史，不得静默覆盖。
9. 你只负责识别和提出结构化变更建议；后端负责校验、写库和工具执行。
10. 不能确定时使用 unknown、低置信度或 needs_clarification，不要强行分类。
11. 严格输出符合 Schema 的 JSON，不输出 Markdown 或额外解释。
```

### 4.4 置信度初始策略

-   `>= 0.85`：可进入自动处理候选，仍须经过权限与风险校验。
-   `0.65–0.84`：可保存、分类并提出关联建议；重要状态变更应确认或采用更严格规则。
-   `< 0.65`：保留原始记录，标记 `unknown` /
    `needs_clarification`，不执行外部动作。

阈值仅为初始默认值，应根据真实数据集校准。置信度不是权限，也不能单独决定是否执行。

## 5. 分级自主模式（Balanced Autonomy）

执行决策必须由后端 Policy Engine 作出，不应只依赖 LLM 自我判断。

  -------------------------------------------------------------------------------------------------------------------------
  级别      行为                示例                                           默认规则
  --------- ------------------- ---------------------------------------------- --------------------------------------------
  A0        保存原始内容        保存录音、转写                                 自动

  A1        内部整理            分类、提取实体、候选关联 Matter                证据充分时自动；否则标记候选

  A2        内部状态更新        更新明确决定、任务状态、截止日期               目标明确且有证据时自动；保留历史

  A3        可逆的内部工作      生成脚本草稿、整理研究、建立提醒               在用户预设范围内可自动；不确定时询问

  A4        外部副作用          发邮件、发送文件、通知合作伙伴、修改外部日历   必须满足明确授权策略；未授权或超范围先确认

  A5        高影响/不可逆操作   付款、购买、删除重要数据、签署、公开发布       默认要求用户明确确认
  -------------------------------------------------------------------------------------------------------------------------

授权应可细化为工具、动作、对象范围、条件和有效期，并允许用户撤销。例如"可读取指定合作项目邮件"不等于"可代表用户向任何人发邮件"。

### 必须暂停并确认的情况

-   收件人、文件、Matter 或操作对象不明确。
-   存在多个合理解释且选错会产生明显影响。
-   操作超出已授权范围。
-   涉及高影响或不可逆操作且没有覆盖该动作的明确授权。
-   新指令与有效决定或正在执行的任务冲突，无法安全自动协调。
-   必要参数缺失、置信度不足或工具结果不确定。

### 执行前检查

1.  意图明确吗？
2.  目标 Matter 和对象明确吗？
3.  必要参数齐全吗？
4.  授权覆盖此动作和对象吗？
5.  风险级别允许自动执行吗？
6.  是否已有相同操作在执行或已成功？
7.  是否有较新的 correction / decision 使操作失效？
8.  能否记录结果并在失败时恢复？

## 6. Matter 状态与事件历史

### Matter 状态

-   `emerging`：想法或候选事项，目标尚未明确。
-   `active`：目标明确，正在推进。
-   `blocked`：受到阻塞。
-   `waiting`：等待他人、外部事件或用户回应。
-   `completed`：目标完成且结果经过验证。
-   `cancelled`：用户明确取消。
-   `archived`：结束后归档。

### 建议的事件类型

`IdeaCaptured`、`DecisionRecorded`、`CommitmentCreated`、`InstructionRequested`、`CorrectionReceived`、`MatterLinked`、`TaskCreated`、`TaskStarted`、`TaskBlocked`、`TaskCompleted`、`PermissionRequested`、`PermissionGranted`、`PermissionRevoked`、`ExternalActionSucceeded`、`ExternalActionFailed`。

事件示例：

``` json
{
  "event_id": "由后端生成",
  "event_type": "DecisionRecorded",
  "matter_id": "matter_456",
  "source_record_id": "rec_123",
  "occurred_at": "2026-10-24T10:00:00-07:00",
  "recorded_at": "2026-10-24T10:00:02-07:00",
  "payload": {
    "field": "current_direction",
    "old_value": "参数测评",
    "new_value": "真人体验"
  },
  "confidence": 0.94,
  "supersedes_event_id": "evt_previous",
  "actor": "user_via_ring"
}
```

规则： - 新决定取代旧决定时，旧决定标记为 `superseded`，不删除。 -
Correction 应指向被修正的事实或状态；无法定位时请求澄清。 -
任务执行期间收到新决定，必须检查任务是否仍有效。 -
尚未执行的旧操作可以取消或重新规划；已经完成的外部操作不能假装撤销。 -
不确定的状态变化可存为 `proposed_change`，等待用户确认。 -
所有关键变更保存来源、时间和原因。

## 7. Agent Runtime：执行、等待、恢复

### 任务状态机

``` text
queued -> planning -> ready -> running
                         |         |
                         |         +-> waiting_external
                         |         +-> needs_user
                         |         +-> succeeded
                         |         +-> failed
                         +-> cancelled / superseded
```

后端校验所有状态转移；LLM 不得自行把任务设为 `succeeded`。

### 执行流程

1.  创建任务并保存来源事件。
2.  Planner 生成步骤与工具调用建议。
3.  Policy Engine 校验权限和风险。
4.  Executor 执行单个步骤并持久化结果。
5.  等待邮件回复等外部事件时进入 `waiting_external`。
6.  外部事件到达后，重新加载最新 Matter、授权和
    correction，再判断是否恢复。
7.  收到 correction 时，先暂停仍可停止的冲突任务，再重新规划。
8.  验证真实结果后才标记成功，并保存证据。

### 恢复与防重复

-   每个步骤持久化输入、输出、状态、工具调用 ID 和错误。
-   使用幂等键，避免重试时重复发邮件或重复创建外部资源。
-   恢复前重新检查权限、Matter 状态和最新纠错。
-   通过外部事件触发恢复，不要求模型持续循环推理。
-   重试有上限和退避策略。
-   外部动作结果不确定时先查询实际状态，不要直接重复执行。
-   用户撤销授权后，未执行步骤必须停止；已完成动作如实记录。

### 8.2 同一案例在三个主要 UI 区域中的呈现

**案例 A：Idea --- "我觉得 AI 眼镜挺值得拍的。"** -
`From your ring`：显示原始录音、转写与"想法"标签；显示"可能关联：AI
眼镜视频"（只有候选证据时才标为"可能"）。 -
`In motion`：默认不新增执行中的任务，因为用户还没有决定要做。 -
`Needs you`：通常不需要出现；只有项目关联有实际影响、且必须用户选择时才显示待确认卡片。

**案例 B：Decision --- "决定了，下期就做 AI 眼镜。"** -
`From your ring`：显示"决定"标签，并注明"已更新：下期内容方向"。 -
Matter：将"AI 眼镜视频"设为当前目标或方向，并保留之前方向的历史记录。 -
`Needs you`：如果"下期"无法定位到具体内容计划，或存在多个候选项目，则询问"你指的是哪个内容计划？"

**案例 C：Commitment --- "我答应摄影师周五给脚本。"** -
`From your ring`：显示"承诺"标签，并展示"交付：脚本 / 对象：摄影师 /
时间：周五"。 -
`In motion`：创建内部交付任务；截止日期只有在日期解析可靠时才转成具体日期。 -
`Needs you`：若无法确定是哪位摄影师或哪一个周五，提出最少必要的问题；不能编造收件人或日期。

**案例 D：Instruction --- "把刚才的脚本发给摄影师。"** -
`From your ring`：显示"指令"标签与执行状态，例如"等待授权""执行中""已发送"或"失败"。 -
`In motion`：仅当操作已获授权并真正开始执行时才显示任务进展。 -
`Needs you`：如果有多个脚本、多个摄影师或发送权限不足，展示明确选择；对外发送成功后必须依据工具结果显示，不得提前显示"已发送"。

**案例 E：Correction --- "不对，上一版不要了。"** -
`From your ring`：显示"纠错"标签，并链接到被修正的决定、脚本或任务。 -
Matter：将旧版本标记为已被取代，保留历史；展示当前有效版本。 -
`In motion`：检查是否有基于旧版本的待执行任务；可安全取消时暂停或取消，并记录结果。 -
`Needs you`：如果系统无法可靠判断"上一版"指什么，询问用户选择版本或项目；不得静默修改错误对象。

### 8.3 UI 状态用词规范

建议在界面中区分以下状态，避免把模型的理解结果误当作实际执行结果：

-   **已收到**：录音与转写已保存。
-   **已识别**：意图分类已完成。
-   **已关联**：已关联到某个 Matter；候选关联必须显示"可能关联"。
-   **已更新**：内部状态已成功写入。
-   **待确认**：需要用户选择、补充信息或授权。
-   **执行中**：任务已经由 Runtime 启动，而不是仅生成了计划。
-   **等待回复**：任务在等待外部事件。
-   **已完成**：结果经过验证。
-   **执行失败**：显示失败原因和可用的恢复操作。

UI 必须遵循实际后端状态；不要仅根据 LLM 的自然语言回复推断执行成功。

### Needs you

展示需要确认、补充信息、授权或解决冲突的事项。卡片应说明：Agent
理解了什么、依据是什么、已经做了什么、尚未做什么、用户需要决定什么。

### In motion

展示正在推进的
Matter、当前阶段、下一步、等待对象、最近执行结果和可靠来源的截止时间。不能把"生成计划"显示为"正在执行"，也不能把工具调用成功等同于业务完成。

### From your ring

展示原始录音、转写、意图类型、关联
Matter、状态更新和执行结果，并允许用户纠正分类或关联。

结果状态必须区分： - `received`：音频已保存。 -
`understood`：完成意图识别。 - `updated`：内部状态变更已写入。 -
`needs_confirmation`：等待用户授权或补充信息。 -
`executed`：外部动作经验证完成。 - `failed`：执行失败并显示原因。

## 9. 端到端测试案例：AI 眼镜视频

### Day 1 --- Idea

用户："我觉得 AI 眼镜挺值得拍的。"

预期：保存原始录音，分类为 `idea`，尝试关联现有
Matter；没有合适事项时保留为独立想法或提出建议。不创建确定发布日期，不联系任何人。

### Day 2 --- Decision

用户："我决定做一期 AI 眼镜视频，重点讲真人体验。"

预期：分类为 `decision`，将想法关联或升级为
Matter，更新目标与方向。除非另有明确授权，不自动联系他人或安排拍摄。

### Day 3 --- Commitment

用户："我答应摄影师周五给脚本。"

预期：分类为
`commitment`，建立交付任务。如果"周五"不能解析为明确日期，保留原始表达并请求澄清或暂不设绝对截止时间。

### Day 4 --- Instruction

用户："把最终脚本发给摄影师。"

预期：分类为 `instruction`，查找
Matter、最终脚本和摄影师联系方式。对象、文件或授权不明确时进入
`needs_user`；若已有明确授权则执行。验证工具结果后才显示"已发送"。

### Day 5 --- Correction

用户："不对，上一版不要了，改成真人体验，不要参数对比。"

预期：分类为
`correction`，定位旧脚本、旧决定和关联任务；旧方向标记为被取代；停止仍可取消的旧任务。可以在授权范围内生成新草稿；向摄影师发送新版仍遵守外部操作权限规则。

### 冲突场景

原计划周五发布，但摄影师表示只能周六拍摄。

预期：关联同一
Matter，检测拍摄时间与发布日期冲突，不继续执行明显过期的排期；提出调整方案。若没有预先授权自动调整排期，则将决策放入
`Needs you`。

## 10. 研发验收标准

### 意图识别

-   五类意图分别评估 Precision、Recall 和混淆情况。
-   能识别一段话中的多个意图。
-   能区分想法、决定、承诺和明确指令。
-   模糊时允许 `unknown` / `needs_clarification`。
-   不将模型推断冒充用户原话。

### 状态正确性

-   正确关联 Matter，避免轻易创建重复事项。
-   新决定可取代旧决定，但历史仍可追溯。
-   Correction 能修正相关状态。
-   任务状态与真实工具结果一致。
-   所有关键状态变更有来源和时间。

### UI 映射与一致性

-   同一条录音在分类结果、Matter 状态和 App UI 中使用一致的意图类型。
-   `idea` 不会仅因被捕捉就自动显示为执行中任务。
-   `commitment` 可以建立内部交付任务，但不会自动对外联系第三方。
-   `instruction` 在权限不足时显示"待确认"，不会伪装成执行中或已完成。
-   `correction` 会显示被修正对象；无法可靠定位时先澄清。
-   "已完成 / 已发送"等成功状态必须有后端验证证据。

### 执行安全

-   未授权的外部动作不会执行。
-   撤销授权后，待执行任务会停止。
-   重试不会造成重复副作用。
-   收到新 correction 后旧计划会重新校验。
-   失败时不会显示成功。
-   对不可撤回的外部操作如实报告。

### 产品价值指标

建议衡量： - 每周有可验证进展的 Matters 数量。 - Ring 相较 Phone
新增的有效意图数。 - Matter 关联准确率、用户纠错率、错误执行率。 -
用户需要补充上下文的次数与时间。 -
避免的漏办事项，以及持续佩戴与付费意愿。

北极星候选指标：**Weekly Agent-Advanced Matters**------每周因 Spur
有效介入而产生可验证进展的 Matter 数量。必须依据可验证事件计算，而不是由
Agent 自行声称"已推进"。

## 12. 实施顺序

### Phase 1 --- 分类与可追溯

1.  定义 JSON Schema。
2.  建立五类意图 Prompt 与测试集。
3.  保存原始录音、转写、分类结果和来源。
4.  在 App 展示分类与 Matter 关联，支持纠错。

### Phase 2 --- Personal Intent State

1.  建立 Matter 与事件历史模型。
2.  实现 Idea、Decision、Commitment、Correction 的状态变更规则。
3.  实现冲突检测、旧决定失效与历史追溯。
4.  映射到 Needs you、In motion、From your ring。

### Phase 3 --- 分级自主执行

1.  实现 Policy Engine 和权限配置。
2.  接入少量低风险工具。
3.  实现任务状态机、Checkpoint、幂等执行与恢复。
4.  逐步扩大自主能力。

### Phase 4 --- 验证产品假设

1.  使用同一 Agent 后端对比 Ring 与 Phone。
2.  衡量有效新增意图，而不是只看录音量。
3.  观察新增意图是否带来 Matter 的实际进展。
4.  根据误分类、错误关联和用户纠错持续改进。

## 13. 最重要的工程原则

**把用户新表达的信息，可靠地转化为个人意图状态的变更；再由有权限、有状态、有检查机制的
Agent 决定下一步行动。**

LLM 负责理解与提出变更建议；数据库保存事实和历史；Policy Engine
决定能否执行；Runtime 管理执行状态与恢复；App 让用户了解并纠正系统行为。

这几部分不能全部交给一个大 Prompt 完成。
