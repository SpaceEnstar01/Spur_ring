# 研强录音戒指按键手势区分调试记录

## 1. 调试目标

区分录音戒指的两种操作：

```text
长按说话，松开停止
→ 智能体指令

双击开始，再次双击停止
→ 普通长录音
```

目标是让 App 将两类录音自动分流到“智能体任务”和“录音”两个场景。

## 2. 当前结论

截至 2026-07-16，暂时无法通过当前厂商公开回调可靠区分两种手势。

两种操作在 App 中都只表现为：

```text
1 idle
→ 2 recording
→ 4 ready_to_sync
```

没有收到双击、长按或松开的独立事件。

本次调试暂时停止，保留测试代码与记录，等待厂商协议、Debug SDK、其他手机 HCI 抓包或固件支持。

## 4. 厂商 SDK 中发现的触控定义

```text
4353 = SINGLE_CLICK
4354 = DOUBLE_CLICK
4355 = VOLUME_UP
4356 = VOLUME_DOWN
4357 = SWIPE_UP
4358 = SWIPE_DOWN
4359 = SWIPE_LEFT
4360 = SWIPE_RIGHT
```

### 4.2 TouchAction 动作定义

```text
257 = SINGLE_CLICK
258 = DOUBLE_CLICK
259 = LONG_PRESS
260 = SWIPE_UP
261 = SWIPE_DOWN
262 = RELEASE_PRESS
```

SDK 虽然定义了 `LONG_PRESS` 和 `RELEASE_PRESS`，但字节码检查中，它们只出现在枚举及转换代码里，没有找到将其传递给 `SmartTouchEventCallback` 的实际引用链。

## 5. 真机触控回调测试

触控上报成功开启：

```text
[YanqiangButtonDebug] reporting: enabled=true result=1
```

依次执行：

1. 两次“双击开始、双击停止”；
2. 两次“长按开始、松开停止”。

四次录音均只收到相同状态：

```text
state: 1 idle
state: 2 recording
state: 4 ready_to_sync
```

没有任何：

```text
touch: action=... code=...
```

因此当前工作状态不包含录音触发来源。

## 6. Android 系统按键测试

执行：

```bash
adb shell getevent -lt
```

操作戒指的单击、双击、长按和松开后，没有新增输入事件。

后来观察到的事件为：

```text
/dev/input/event1 KEY_POWER
/dev/input/event3 touchpanel
```

它们分别来自手机电源键和手机触摸屏，不是戒指。

结论：戒指没有作为 Android HID、键盘或媒体按键设备上报，不能通过 `MainActivity` 的普通 `KeyEvent` 监听区分。

## 7. 厂商 SDK 字节码检查

检查对象：

```text
aizo_serversdk_release_v2_2.2.6.aar
```

SDK 的 `BeDataReceive` 只有收到专用智能触控 BLE 数据后，才会创建：

```java
SmartTouchEventModel(time, event)
```

单条记录结构为：

```text
6 字节时间 + 2 字节事件码
```

随后才会调用：

```java
SmartTouchEventCallback.onSmartTouchEvent(...)
```

本次测试完全没有触控回调，说明录音按键没有进入这条公开智能触控事件链。

## 8. Bluetooth HCI 抓包尝试

测试手机为 ColorOS/Oplus 系统。

开发者选项已开启“蓝牙 HCI 信息收集日志”，并生成 Bug Report：

```bash
adb bugreport /Users/spur/Desktop/yanqiang-hci/yanqiang-ring
adb bugreport /Users/spur/Desktop/yanqiang-hci/yanqiang-ring-2
```

Bug Report 中存在：

```text
FS/data/misc/bluetooth/logs/bthci/.../BT_HCI_*.cfa
```

但每个 `.cfa` 只有 16 字节。内容仅为合法的 `btsnoop` 文件头：

```text
btsnoop + version + datalink type
```

没有任何实际蓝牙数据包。

标准配置最初未生效：

```bash
adb shell settings get secure bluetooth_hci_log
# null
```

手动设置成功：

```bash
adb shell settings put secure bluetooth_hci_log 1
```

但完整模式属性为空，普通 ADB 无权修改：

```bash
adb shell getprop persist.bluetooth.btsnooplogmode
# 空

adb shell setprop persist.bluetooth.btsnooplogmode full
# Failed to set property
```

结论：当前 ColorOS 手机限制普通 ADB 开启完整 HCI 抓包，生成的 HCI 文件为空。

## 9. Logcat 抓取尝试

执行：

```bash
adb logcat -c
adb logcat -v threadtime > /Users/spur/Desktop/yanqiang-hci/ring-actions.log
```

在命令运行期间完成双击录音和长按录音。

生成文件约 365 KB，但内容只有手机系统日志，没有：

- 厂商 SDK 原始命令；
- 戒指 MAC；
- ATT Notify 载荷；
- 智能触控事件；
- 可用于比较手势的原始十六进制数据。

推断厂商 Release SDK 没有输出底层 BLE 原始日志。

## 10. 当前技术判断

目前证据更支持以下流程：

```text
戒指固件内部识别双击或长按
→ 固件直接控制录音开始/停止
→ 只向手机上报 recording / ready_to_sync
→ 不上报录音触发手势
```

但由于未获得有效 HCI 原始数据，暂时不能排除“存在不同 BLE Notify，但 Release SDK 未转发”的可能。

## 11. 未来恢复调试的优先顺序

### 方案一：向厂商确认

向厂商提供以下问题：

> 开启 `setTouchEventReportSwitch(1)` 后，双击录音和长按录音均只收到 `DeviceWorkingState 1/2/4`，`SmartTouchEventCallback` 没有回调。请问 SDK 或固件是否提供区分“双击录音”和“长按说话”的 trigger source、按下/松开事件或录音文件类型字段？`LONG_PRESS=259`、`RELEASE_PRESS=262` 应如何启用？

优先索取：

- 按键/触控协议文档；
- Debug 版 SDK；
- 原始 BLE Notify 回调；
- 包含 trigger source 的新固件；
- 长按实时音频流接口。

### 方案二：更换抓包手机

使用支持标准完整 HCI snoop 的 Android 手机重新测试，要求：

```text
persist.bluetooth.btsnooplogmode = full
```

并能够生成包含实际数据包的：

```text
btsnoop_hci.log
```

分别对比：

```text
双击开始 vs 长按开始
双击停止 vs 松开
```

### 方案三：底层 SDK 插桩

如果不能更换手机且厂商无法支持，可研究对厂商 AAR 的 BLE 接收层做 Debug 插桩，在 `BeDataReceive` 解析前记录原始命令和字节。

该方案风险较高，应在 SDK bundle 副本上实验，不直接修改当前已经跑通的正式闭环。

## 12. 临时产品策略

在硬件触发来源可用前，不建议仅凭录音时长强制分类。

临时可选：

```text
App 手动选择“智能体模式”或“录音模式”
```

或者：

```text
按时长给出默认分类，但允许用户立即修改
```

时长只能作为推断，不能可靠证明用户使用的是双击还是长按。
