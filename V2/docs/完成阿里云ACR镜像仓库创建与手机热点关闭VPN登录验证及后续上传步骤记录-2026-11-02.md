### Playwright MCP 网页任务验证（部分通过）

用户在无 VPN 状态下从 ACK Workbench 执行真实请求，要求 Agent 使用 Playwright MCP 打开 `https://example.com/` 并读取标题。HTTP API 返回 200，run ID 为 `f63e05de-f391-4398-adf0-d89bcd42a5db`。Agent 报告 Playwright 浏览器连续两次启动失败，错误表现为 Chromium Zygote 子进程异常退出；随后走通用 `web_fetch` 回退，拿到 HTTP 200 和 Example Domain 标题/主标题。返回 sources 仅显示 `web fetch`。

结论需分开表述：ACK Pod 出网和通用网页抓取可用；真实模型及 DSH 可执行回合；但 Playwright MCP 的 Chromium 尚未启动成功，指定的浏览器验证失败。因此 Docker 本地使用的 Playwright 官方 seccomp profile 尚未映射到 ACK Pod 的运行安全策略。本次无 VPN 与浏览器启动失败没有因果关系；失败发生在 Chromium 进程启动阶段，且回退抓取已证明网页可从 Pod 访问。

后续检查中，Pod 的 `.spec.securityContext.seccompProfile.type` 和容器级对应字段均为空；容器内 `/proc/1/status` 返回 `Seccomp: 0`，表明该进程当前没有 seccomp syscall filter。Pod 内 `/proc/sys/user/max_user_namespaces` 为 `0`，而 `/proc/sys/kernel/unprivileged_userns_clone` 为 `1`。在 Pod 内以非 root 用户直接启动 `/opt/google/chrome/chrome --headless ... --dump-dom about:blank`，Chromium 明确输出 `Failed to move to new namespace ... failed: errno = Operation not permitted`，随后 Zygote 以状态 1 退出。这将故障收敛到容器/节点创建 Chrome sandbox namespaces 的权限/策略路径，而不是 VPN、网页网络或 SiliconFlow API。

镜像中的 `/opt/google/chrome/chrome-sandbox` 存在，属主为 `root:root`，权限为 `-rwsr-xr-x`；容器运行用户为 UID 10001。尚未确认 setuid helper 是否能在该容器 capability/mount 策略下运行。下一步以 `CHROME_DEVEL_SANDBOX=/opt/google/chrome/chrome-sandbox` 显式选择该 helper，直接启动 `about:blank` 做无业务改动的验证。Chromium 官方资料说明该环境变量可指定 helper 路径。若 helper 仍无法工作，再评估 `user.max_user_namespaces`；该设置可能改变共享节点上其他进程的 namespace 能力，应先评估集群团队策略，避免直接在共享 ACK 节点上永久开启。禁止以 privileged、宽泛 capabilities 或 `--no-sandbox` 作为默认修复。根因修复后再复测同一只读网页任务。

### 2026-11-03：setuid 沙箱助手复测与故障边界

用户在 ACK Workbench 使用以下命令显式指定镜像内的 Chrome setuid 沙箱助手：

```bash
kubectl exec -n spur-agent spur-agent-check -- sh -c 'CHROME_DEVEL_SANDBOX=/opt/google/chrome/chrome-sandbox timeout 20s /opt/google/chrome/chrome --headless --enable-logging=stderr --v=1 --no-first-run --user-data-dir=/tmp/chrome-ack-suid-diagnostic --dump-dom about:blank 2>&1 | tail -50'
```

结果仍为 `Failed to move to new namespace ... errno = Operation not permitted`，之后 Zygote 以状态 1 退出。再检查容器进程：`CapEff: 0000000000000000`、`NoNewPrivs: 0`、`Seccomp: 0`；根文件系统 overlay 挂载选项为 `rw,relatime`，输出中未见 `nosuid`。因此显式指定 helper 仍未解除故障。当前可确定的故障边界是：Chrome 在 ACK Pod 内创建 PID/网络 namespace 被拒绝；`user.max_user_namespaces=0` 是重要限制证据，但仅凭这些输出还不能断言唯一拒绝点，也不能证明单独更改该 sysctl 就会修复。

#### ECS 方案的可行性判断（架构分析，尚未实机验证）

独立 ECS 虚拟机由项目方控制 Linux 主机配置，理论上可以在核实内核能力与安全要求后，为 Chrome 配置受控的 namespace 沙箱，并运行 Agent。它能避开当前 ACK Pod 的调度和容器安全策略边界，**但购买 ECS 本身不保证 Chrome 自动可用**：如果继续用 Docker，仍需正确配置容器的 namespace、seccomp 和所需权限；若直接在主机运行，则仍需验证宿主机的内核 sysctl、Chrome helper 与主机安全策略。不能以 `--no-sandbox` 或 `--privileged` 作为默认方案。

需要区分“独立 ECS 主机直接运行 Agent”和“在独立 ECS 上用 Docker 运行 Agent”。前者对 Chrome 沙箱问题通常更容易排查与配置，但偏离当前容器交付路径；后者保留镜像部署方式，配置方式仍须单独验证。现有 ACK 节点本身也是 ECS，但属于共享集群节点，不应未经集群管理员同意而在宿主机安装或更改内核设置。

建议先在不承担业务流量的隔离环境做同一镜像验证：保持非 root、Chrome 沙箱开启，运行 `about:blank` 和公开网页只读测试；确认通过后再决定部署形态。此次分析不是 ECS 上的成功测试，也不代表已采购或变更任何 ECS/ACK 资源。
