# 主工程火山引擎云端语音转写与 V2 苹果本地识别现状及后续切换接续记录

核对日期：2026-11-04。本文记录源码核对结果，不代表云端实时部署状态；本次未修改转写实现或部署服务。

## 1. 当前结论

- 主工程保留了火山引擎云端语音转写代码。
- 当前 V2 App 的录音转写使用 iPhone 本地 Apple Speech，没有调用上述云端转写接口，也没有失败后自动上传音频的回退。
- 后续希望复用云端高质量转写，再接入意图判断与 Personal Agent；尚未执行切换。

## 2. 当前 V2 App 链路

```text
手机录音
  → iPhone 本地 Apple Speech 转写
  → 用户提交转写文字
  → 硅谷 ECS Personal Agent
  → 执行任务并返回结果
```

源码位置（相对主仓 `/Users/x/X/space/spur`）：

- `V2/appV2/app_mobile/src/services/transcriptionApi.ts`：调用原生 `transcribeRecording`；无云端转写请求或回退。
- `V2/appV2/app_mobile/native-sdk/ios/PhoneAudio.m`：使用 `SFSpeechRecognizer`，语言 `zh-CN`，设置 `requiresOnDeviceRecognition = YES`；包含本地兼容识别路径。
- `V2/appV2/app_mobile/native-sdk/ios/SpurFileSpeech.swift`：Apple Speech 文件识别兼容实现。
- `V2/appV2/app_mobile/src/services/automaticReplies.ts`：`submitRecordingToPersonalAgent` 将转写文字提交给 Personal Agent。
- `V2/appV2/app_mobile/src/services/creatorAgentApi.ts`：Personal Agent 的地址、Bearer 令牌、健康检查和任务请求。

用户实测本地转写速度快，但识别准确率存在问题。这是此次讨论恢复云端转写的原因，不是两种方案的全面质量对比。

## 3. 主工程原有云端处理链路

```text
App 录音
  → 上传音频文件到 POST /api/audio-task
  → 主工程音频后端保存文件
  → 按需通过 FFmpeg 转换音频格式
  → 火山引擎 ASR 返回转写文字
  → 按 taskType 分流
      ├─ recording_summary：全文润色 → 会议纪要
      ├─ agent_command：普通指令交给大模型；其中可判断是否需要生图
      └─ agent_image：生成图片
  → 返回转写、处理结果、报告及邮件处理信息
```

源码位置：

- `app/mobile/src/services/audioAgentApi.ts`：`processAudioWithAi` 通过 multipart 上传音频到 `/api/audio-task`。
- `app/mobile/src/services/localRecordingAnalysis.ts`：以 `recording_summary` 调用上述接口。
- `app/cloud/audio-agent/src/server.ts`：`handleAudioTask` 接收音频、调用转写、按任务类型处理并返回结果。
- `app/cloud/audio-agent/src/stt/index.ts`：按配置选择 `mock` 或 `volcengine`。
- `app/cloud/audio-agent/src/stt/volcengine.ts`：格式转换、火山快速识别，以及录音 URL 提交任务后轮询结果。
- `app/cloud/audio-agent/src/stt/saucBigmodel.ts`：另一路语音识别实现，具体入口需结合 `server.ts` 核对。
- `app/cloud/audio-agent/src/meetingNotesPipeline.ts`：录音全文润色与会议纪要流水线。
- `app/cloud/audio-agent/src/taskPrompts.ts`：任务类型与提示词。
- `app/cloud/audio-agent/src/agent.ts`：配置大模型 API Key 时直接调用 Chat Completions，否则走本地 Agent 子进程路径；不能把所有旧请求都视为已有工具执行能力。

注意：存在源码不等于硅谷 ECS 当前已经运行该音频后端。默认 STT 可能是 mock，恢复真实转写时需核对配置与凭据；本文不保存任何密钥。

## 4. 用户期望的后续链路

```text
录音上传云端
  → 高质量语音转写
  → 队列／批处理
  → 快速意图判断
      ├─ 想法：保存、呈现
      ├─ 决定／承诺／目标：形成可跟进信息，按规则推送 App
      └─ 需要进一步执行的请求：交给 Personal Agent 深度处理
  → App 展示状态与结果
```

这属于目标架构，不能标记为已经全部实现。本次核对到的主链路是单条音频上传、转写及按任务类型处理，尚未据此证明完整的多录音批处理、个人意图分类和主动推送体系已经落地。

火山接口的“异步提交任务并轮询”不等于我们自己的“多录音批处理队列”。想法、决定、承诺、目标的识别也不等于现有的会议／指令／生图任务分类。决定或承诺本身不应自动等同于外部行动授权。

## 5. 后续切换时的接续要点

1. 以最新 V2 App UI 为基础，复用主工程音频后端，不引入队友的 Java 后端作为默认前提。

3. 将“语音转写”和“Personal Agent 执行”分成可独立重试的阶段，保留原音频与原始转写。
