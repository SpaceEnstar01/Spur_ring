Spur Harness：投资人问题分析与落地方案

日期：2026-10-05

性质：方案与验证计划，不是已上线能力声明

1. 先回答投资人真正关心的事

依据用户提供的会议问题整理，夏令最关心的是：戒指降低记录摩擦之后，Spur 能否稳定减少博主从零散想法到可拍摄脚本的工作量，以及这种价值能否带来持续付费。

这需要四类证据：明确的一类用户、可重复的创作闭环、可恢复的后台工程、真实使用效果。会议角标与原话未通过原始录音独立核验；本分析不把整理中的结论视为投资人逐字承诺。

现阶段建议聚焦：同时推进多个选题、经常随口记录素材、需要持续产出短视频脚本的创作者。 是否以内容变现为目标可以作为招募条件，但不是系统自动提高收入的保证。

整体个人助理愿景继续保留，订车、订票、编程和情绪陪伴放在未来方向。当前付费价值验证集中在：想法保存、并行选题理解、素材组织、脚本生成与持续修改。

2. 从九组问题中学习什么

人群与术语

随身录音、编程输入、个人助理不能仅因共享语音入口就被当成同一需求。先用创作者场景证明一条业务线。对外表述建议使用“随口记录与对话创作”，不要使用容易被理解为代码生成的 whisper coding。仓库里的 Spur Flow 是语音输入产品定义，与这里的 Agent Flow 创作流程需区分。

行动深度

Y 轴不要用工具数量或 Agent 数量衡量。建议按可观察成果递进：可靠记录 → 找回相关素材 → 分清并行选题 → 形成可拍摄脚本 → 基于反馈持续修改与交付。初期达到脚本可用与修改可靠，就可以验证价值，无须先做到通用自主执行。

自动归档与上下文

关键词相同不等于创作目标相同。自动归档本质是判断“这条素材能支持哪个选题的什么观点”，而不只是预测标签。归档不确定时先暂存，允许低摩擦纠正；误归档造成的串题可能比暂未归档更伤害信任。

多模态与工作流

同一个对话应接收语音、文本、截图、链接和用户有权提供的视频。都转换成统一素材对象并保留来源。链接不可访问时让用户补截图或文件，不能假装已经读取；不承诺直接控制或读取所有第三方平台。

生态位与订阅

Spur 自己掌握创作项目状态、素材关联、时间线、成果版本和评价标准；模型、OCR、搜索、文档生成及外部 Agent 可以替换。这样中枢价值来自创作连续性。是否值得订阅，要看使用者节省时间、采用成果和实际续用，不以“Manus 级”或 token 数量代替验证。

3. 竞争前提需要更新

核验时 flomo 官方文档已列出相关笔记、AI 洞察、Agent、记忆档案和 MCP；其 Agent 支持对话与写回。不能据此声称 flomo 没有上下文或 Agent。官方也说明其核心是记录、整理与回顾，复杂文档和项目管理并非主要方向。flomo 官方 FAQ

Spur 的差异化假设是：围绕一个持续演进的创作项目，维护素材用途、观点变化、脚本结构与修改历史，把用户交代的事情推进到可用成果。 这仍需和当前竞品、普通大模型对话进行同条件比较；没有测试数据前，只能称方向，不能称已经领先。

4. 五个“国庆”选题，系统应如何处理

假设用户并行推进：A 亲子避拥堵攻略、B 民宿商业观察、C 假期独处情绪、D 节后效率、E 假期消费复盘。以下为设计示例，不是真实用户数据。

“大家想去人少的地方，但交通也要方便”：可能支持 A；缺乏上下文时暂存或提出两个候选。

“老板说满房不代表赚钱，平台抽成太高”：可支持 B，保留“用户转述老板观点”的来源属性。

“看朋友圈都在旅游，反而觉得自己很孤独”：支持 C，不能仅凭“旅游”归到 A。

“前三条其实都想放到民宿那期”：用户明确纠正后，更新关联并记录纠正事件，保留原素材。

同一条素材可以关联多个选题，但每个关联要有用途说明，不强制单一文件夹。

系统判断依据：用户明确指向 > 当前任务与最近对话 > 选题目标、受众、核心观点和排除条件 > 语义及关键词相似度。时间接近只是辅助证据。

建议为每个选题保存轻量创作说明：写给谁、要回答什么、主张是什么、目标形式、当前阶段、已采用素材、排除内容与待补信息。不让用户一次填完，优先从对话提取，关键歧义再询问。

5. Harness 应搭哪些东西

5.1 保存层：先收下，再处理

戒指、App 与通知回复都写入统一入口。客户端先保存待上传记录，服务端持久化成功后返回确认；“本机已保存”和“已同步后台”明确区分。原始内容与 AI 整理结果分开保存，避免润色覆盖用户原话。

每条记录保存用户标识、输入标识、来源、录制时间、接收时间、时区、原文或转写、附件引用。设备时间不可靠时标注；模型结果、纠正和任务事件另行记录。幂等键防止重复上传，失败可补传。

“全部想法”指用户主动提交且选择保留的内容，包括尚未归档或未采用的想法；不是持续偷录，也不妨碍用户删除与导出。删除要同步处理原文、派生索引和相关引用，时间线不能成为无法删除个人内容的理由。

5.2 数据对象：对话之外还要有创作项目

Capture： 原始输入及附件，不可被摘要替代。

IdeaUnit： 从一次输入中拆出的独立想法，引用原文片段。一段录音可能包含多个想法。

Topic： 持续选题、创作说明和阶段，拥有稳定标识。

Association： 想法与选题的关联、用途、判断依据及用户纠正状态。

Task： 用户要求的动作、当前状态、检查点和待确认项。

ArtifactVersion： 脚本或文件版本、修改基础及来源引用。

Event： 记录、关联、生成、纠正、采用、失败与恢复的事件。

对话是用户操作这些对象的入口；不能只把长聊天记录作为全部业务状态。

5.3 关联层：候选检索与可纠正归档

先按用户和有效选题过滤，再结合文本检索、语义检索与创作说明找候选。模型判断关联用途，允许归入多个选题、新建候选选题或暂不关联。

不要将模型自报“90% 确信”直接当成准确概率。使用标注样本检验归档表现并校准策略：明确指向可自动关联，存在竞争候选时建议，关键信息不足时暂存或问一个简短问题。用户纠正更新关联和相关索引，不能只改界面显示。

5.4 上下文层：完整存储，按需取用

一次脚本任务只取当前选题说明、相关原文、用户最新修改要求和当前成果版本；必要时补查其他素材。用户偏好只保留确认过或反复验证过的信息，区分偏好与本次要求。摘要用于导航，关键事实回到原文核验。

这与上下文工程的基本原则一致：模型上下文有限，需要有选择地组织相关信息，而不是无限增加历史。Anthropic 上下文工程

5.5 编排层：固定骨架，允许必要调整

首期工作流：保存 → 理解记录或执行意图 → 关联选题 → 组织素材 → 根据要求生成脚本 → 检查 → 对话交付 → 修改新版本。

记录模式默认只保存和轻量关联；用户要求生成时才进入生成任务。缺事实、受众或商业约束时，先询问或明确待补项。模型选择有限工具，工具参数与状态迁移由程序校验；不必先做多 Agent 系统。

每个任务有稳定标识、检查点、重试次数和取消状态。服务端队列或任务系统负责断线后继续，不依赖用户打开手机页面。外部动作重试前查询已有结果。

5.6 交付层：可拍摄、可追溯、可修改

首期脚本建议包含：标题与开场、核心观点、口播段落、画面建议、预计时长、待补事实和采用素材。文本与镜头建议需适配目标平台和用户习惯，但事实不够时不能编造。

“改开头，正文保留”要基于指定版本局部修改；建立新版本并说明变化。手动修改回传后明确新基础版本。最终成果通过对话展示，悬浮窗和通知提供摘要与入口。

PDF/PPT 是可选的交付包装，不能代替脚本质量。首期不自动对外发布；创作与发布授权分开。

5.7 评测层：知道失败发生在哪里

记录检索候选、实际使用素材、归档结果、工具调用、成果版本及用户反馈，不采集模型内部思考作为产品时间线。用户修改可能是新需求，不全部等同于模型失败。

纠正积累成可回归测试的样本；新模型或新流程先验证，再发布。反馈飞轮是工程流程，不等于模型会自动训练得更好。

6. 仓库现状与缺口

本次是有限范围的静态代码阅读，没有运行部署系统或端到端验证。

`app/mobile/src/services/localAgentCards.ts` 已有卡片模型、转写与输出保存、音频处理调用；存储为本地 JSON。类别识别主要是关键词，不能等同于创作选题理解。

`app/mobile/src/services/officeJob.ts` 已有文档生成状态与进度文本，运行任务使用进程内 Map；这不证明服务端持久化调度和断线恢复已成立。

`agent/gateway/README.md` 描述 PDF/PPT 接口。可作为交付基础，实际质量与可用性仍需验收。

`agent/memory/`、`agent/trajectory/`、`agent/eval/` 本次列出的文件只有 README，定义了方向，尚不能证明该目录实现了长期记忆、完整事件账本和黄金集。

上游 runtime 存在不代表业务闭环已经实现；选题关联、成果版本和创作者评测需要独立验收。其他目录或部署端可能有未检查实现，应继续核验。

重要缺口示例：现有本地卡片按音频文件同步，文件消失时卡片可能不再保留；成果修改覆盖当前输出。长期想法资产应独立于音频文件生命周期，修改应保留版本。

7. 怎样证明 Y 轴价值

同条件比较

招募少量具有并行选题需求的真实创作者，先做访谈与一周真实素材采集，再做小规模交叉试用；这是探索计划，不预设统计显著性。参与者使用自己的授权素材，其他用户数据不得串入。

比较普通大模型对话、当前 flomo 及可用连接流程、Spur 创作流程。输入素材、目标和截止条件相同；允许竞品使用真实可用功能，不故意削弱基线。轮换顺序，尽量盲评脚本成果，包含首次使用与使用一段时间后的任务。

核心测量

归档质量： 以用户确认关联为参考，分别测正确关联、误关联、漏关联和需要询问的比例；多选题按多标签评价。

找回质量： 相关素材召回与无关素材混入，特别观察相同关键词下的串题。

脚本采用： 生成后是否被接受进入拍摄准备，用户实际修改耗时，不只看点赞。

总劳动量： 从取材、整理、提示、纠正到脚本可用的全部操作时间，与个人现有方式比较。

可靠性： 故障注入测试下的记录丢失、重复事件、错误版本和恢复成功；不能只测正常网络。

成本与延迟： 每个被采用脚本的模型、转写、存储和工具成本，待处理时间与响应延迟。

商业验证： 持续使用、真实购买意愿与可用产品中的付款或续费；短期偏好不等于长期留存。

先建立基线，再和试用者约定有意义的改善目标；不能捏造“提升 80%”等结果。观看量、收入受选题、分发与账号影响，暂不直接归因给 Harness。

8. 优先实施顺序

第一阶段：可靠保存与找回。 统一输入标识、事件记录、同步确认、删除导出和断线恢复。做到“昨天说的那条能找回”。

第二阶段：并行选题理解。 建立选题说明、多关联、暂存与对话纠正。用五主题共享关键词样本测串题；未达到可接受水平前不扩大自动归档。

第三阶段：脚本与局部修改。 从指定选题调用真实素材，生成可拍摄稿并保留引用与版本；用户可以持续修改。

第四阶段：日常工作流与触达。 接入截图和链接，提供用户选择的每日回顾、创作待办、悬浮摘要与通知。权限差异遵循已有产品文档，不阻塞 App 核心闭环。

第五阶段：验证订阅价值。 在真实创作中比较效果、成本、采用与续用，再决定增加文档格式或外部执行范围。

阶段按验收结果推进，不以未经估算的开发周数承诺完成。

9. 面向投资人的演示与回答

建议演示：五个选题共用关键词 → 十几条混合来源素材进入后台 → 用户纠正一次归属 → 指定选题生成脚本 → 只修改开头 → 关闭页面再回来 → 查看版本与原始素材。样本需明确标注演示数据还是授权真实素材。

回答结构：

我们当前聚焦持续产出内容、并行推进选题的创作者。戒指解决即时输入；Harness 维护原始素材、选题上下文、任务状态和脚本版本。用户通过对话要求整理与创作，系统选择相关素材推进到可修改的脚本。我们的差异需要通过串题率、总修改耗时和脚本采用证明。现在已有转写卡片与文件生成基础，选题关联、持久化时间线和创作评测是接下来的重点；已完成部分与规划部分会分别展示。

投资人要看的不是模块名称，而是：新素材能否接对、任务能否接续、成果是否可用、纠正后是否变好，以及用户是否愿意为此持续付费。
