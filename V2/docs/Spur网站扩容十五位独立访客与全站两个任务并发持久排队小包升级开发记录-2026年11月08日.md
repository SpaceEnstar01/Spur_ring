# Spur 网站扩容十五位访客与两个任务并发排队

日期：2026-11-08。当前阶段：本地代码与小包准备完成，尚未由用户在 ECS 执行此次升级。

## 已有线上证据

用户回传：`WEB_HTTPS_HTTP=200`，`api.hispurring.com` 无凭据访问仍为 401。真实访客任务 `a49716cb-8989-4125-9e29-b06e7d016025` 返回 202，另一访客任务查询 404；本人文件 200，另一访客文件 404；输出 `GUEST_REAL_TASK_AND_ISOLATION_PASS`。这属于升级前两位访客环境的真实验证，不能代替十五位升级后的验收。

## 此次实现

- `V2/web/guest/queue.mjs`：单网关进程持有私有 `queue.json`，任务请求写盘后进入队列。最多两个 dispatching/running 任务；每位访客最多一个正在执行的任务。等待队列上限 150 个。
- 按入队顺序选择当前可运行的任务；同一访客串行时允许另一访客使用空闲名额。结束、失败后自动派发下一项。网页关闭、退出登录不取消已接受任务。
- 丢失回执或网关重启后只 GET 查询原编号，不重新 POST。不确定的任务继续占用名额，避免突破并发限制或重复外部写入；长期无法确认时需管理员检查，不会自动猜测失败或超时释放。
- `gateway.mjs`：提交仍返回 202，排队任务查询返回兼容现有前端的 running 状态并附带 queue.state/position/active/limit。任务及文件查询仍先做访客所有权检查，运行中的工具活动继续从独立 worker 返回。队列启用由私有数据目录的 `queue-enabled` 文件控制。
- `src/taskApi.ts`、`src/Conversation.tsx`：保留排队元数据，显示排队位置、当前执行任务数和自动开始提示。正常运行及成果展示沿用原页面。
- `expand-fifteen-ecs.py`：Python 3.6 兼容，沿用现有镜像、已验证 loader wrapper 和原两位账号。补齐 friend-3 至 friend-15，各自独立容器、Bearer、数据卷及回环端口 4302–4314。复制的凭据仅包含模型服务配置，不包含个人平台授权。
- 十五个 worker 可以空闲存活；任务并发在网关控制。容器内存上限不是预留内存，不能把十五个 1536MB 上限解释为已占用约 23GB。脚本要求执行前 MemAvailable 至少 5GiB；实际常驻内存与浏览器峰值仍需 ECS 验收。
- 新账号各十次任务/日；邀请码默认七天兑换期，兑换后登录有效期三十天。邀请码保存在服务器私有文件，不写入本包或聊天。

## 升级边界

小包只包含新 gateway、queue、扩容脚本和前端 dist，无镜像、模型密钥或浏览器会话。脚本不修改 Caddy 或个人 Agent，不重建现有两位 worker。切换时会暂停访客网关，并检查所有 guest worker 无 running 任务；如发现运行中任务，恢复网关并停止升级。切换前备份原 release 和私有数据；切换失败尝试恢复旧 release 并启动网关。新增访客、容器、卷可能保留，便于检查及续作，不自动删除数据。升级完成前不要分发新码。

仍是单网关进程架构。不能同时启动两个指向同一 queue.json 的网关副本，否则无法保证全局两个名额。文件持久化用于进程重启恢复，不等于断电事务保证。后台任务时长仍受现有 worker 执行限制约束，不宣称支持连续运行两天。
